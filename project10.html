Flow-Matching Language Model

Instead of writing one word after another, this model writes all 64 positions at once. It starts from random noise and moves every position, step by step, toward the point of a real word. A small Transformer learns which way to move. We compare it with an autoregressive model and a masked diffusion model of the same size, trained on the same number of words. Everything runs on a CPU.

Question: can a small continuous flow-matching model write coherent text, and where does the step from continuous points back to words succeed or fail?

Start here: the basic ideas

Every token is a point. Project 1 already gave every one of the 8,192 tokens a list of 384 numbers (its embedding). A 64-token text is then a cloud of 64 points in a 384-dimensional space. Turning a point back into a word is easy: take the word whose point is nearest.

Flow matching teaches a network a velocity: for any half-noisy cloud and a time t between 0 and 1, which way should each point move? Training uses straight lines: pick a noise cloud x0 and a real text x1, take the point x_t = (1 − t)·x0 + t·x1 part-way along the line, and ask the network to predict the direction x1 − x0. To write new text, start from fresh noise and follow the predicted arrows from t = 0 to t = 1 with an ODE solver (small straight steps).

64 marbles are thrown randomly onto a huge board where every word has its own hole. The network is a wind that, step by step, blows each marble toward a hole. For a good sentence, the marbles must end in holes that fit together — and the wind decides where each marble goes from where it starts.
noise (64 × 384)→velocity Transformer, 8–64 steps→64 points→nearest word for each→text

How it differs from earlier projects: AR (Projects 1–2) picks one token at a time from left to right; masked diffusion (Projects 3–6) starts from all-[MASK] and fills in real tokens over several steps. The flow model never picks a token until the very end — everything happens with continuous numbers.

Why word salad? The averaging problem

Suppose the right continuation of "Lily went to …" is one of three two-word phrases, equally likely: the park, her room, a shop. Every one is fine. Now compare two ways to choose.

Lilywentto??

Press a button a few times.

Choosing each position on its own gives "the room", "her shop", "a park" two times out of three. A flow model trained with squared error is pushed toward the average of all fitting texts at every position, and the diagnostics (Phase 10) show that it fixes most positions early (75% by t = 0.2), while it still cannot tell which sentence it is writing. Each position then settles into "some story word" largely on its own. With 48 positions and thousands of words, that is word salad.

Setup, data and baselines

Phases 1–2

What and why

Same CPU and library versions as Projects 1–9 (Python 3.12, torch 2.14 CPU, 24 threads). Every file read from other projects is hashed in results/metrics/env.json; those projects are never changed. The toy 2D problem (above) was solved first to check the method before any text.

Data: the first 64 tokens of each TinyStories story (1,772,187 training openings, 113M tokens), split by story from Project 1's data. A fixed length is needed because the flow moves a fixed-shape cloud. 300 held-out openings with more than 64 tokens are the comparison task; 100 others ("dev") are used for choices.

Baselines (unchanged, from earlier projects): AR-5.3M (Project 2), MDLM-5.3M (Project 3), both trained on 49M tokens — the same as the flow model — and AR-13.9M / MDLM-13.9M as stronger references.

3

Choose a continuous representation

frozen 384-d embeddings

What and why

We use Project 1's trained token embeddings, frozen (a learned space can shrink all words together and make the loss look small while making words impossible to tell apart). They are shifted and scaled so the data has mean 0 and spread 1, like the noise.

Take-away

Words are far apart in this space, so rounding a point to a word is not the hard part. Any failure must come from where the model's points end up.

4

Path, velocity Transformer and loss

Phases 4–6

Path

Straight line from noise to data: x_t = (1 − t)·x0 + t·x1, target velocity x1 − x0. From any velocity guess v we can read the model's current guess of the clean text: x1_hat = x_t + (1 − t)·v.

Model

A bidirectional Transformer (every position sees all others): 4 layers, 4 heads, width 256, 5,178,752 parameters. The time t enters each layer through adaLN-Zero: it sets a scale, shift and gate of each layer norm, and the gates start at zero so training starts stable. A flag marks positions that are clean prompt tokens.

Loss

Mean squared error between predicted and true velocity on valid positions. Half of each batch has a clean prompt of 8–24 tokens (not in the loss), so one model learns both free writing and continuation. 15 unit tests check the path, the solvers, shapes, masks and the embeddings.

Main run

6,000 steps × 128 × 64 tokens, 25,300 tokens/s, 1.8 GB memory, stable. Validation MSE fell from 2.0 to 0.643, still slowly improving. The model's guess of the true token from heavy noise (t = 0.1) reached 30%; at t = 0.3 it is 92%.

But: a model trained 3× shorter (2,000 steps, MSE 0.696) writes text that is just as good — or bad. A lower flow loss did not buy better text (Phase 14).
8

ODE sampler and decoding

Phases 8–9

Solvers

Euler: x ← x + h·v(x, t), one network call per step. Heun: take an Euler step, measure the velocity at the end too, and use the average of the two — two calls per step but more accurate. Both are 30 lines of hand-written code; every network call (NFE) is counted.

Decoding

Each final point becomes the token with the nearest embedding, or the token with the highest score from the projection head (the output layer of Project 1's model). Chosen on the 100 dev prompts only: Heun, 32 steps (64 calls), nearest. Projection was 3.4× worse and produced 24–42% words that are not in the vocabulary list.

10

Diagnose the continuous–discrete gap

where exactly it fails

Four measurements

  • Decision time: along the real sampling path, 61% of final tokens are already fixed at t = 0.12 and 80% at t = 0.25 (chart in "Why word salad?").
  • Decodability: if a real text is behind the noise, the model's guess is right for 30% of tokens at t = 0.1 and 80% at t = 0.2. Between t = 0.2 and 0.4 it is even worse than simply rescaling the noisy input.
  • End points: generated points end 13.5 away from the nearest word (clean words: 0; words are 19 apart). They stop in the empty space between words; more steps barely help (14.8 → 13.6).
  • Frequent words: not over-used (60.6% of tokens among the top 100, real text 63.3%).

Noise or prompt?

Same starting noise, with and without the prompt: 74% of the 48 tokens are identical. With a different prompt: 73%. Same prompt, different noise: 2%. Where the noise starts decides the words.

Diagnosis

The squared-error velocity points to the average of all texts that fit the current noisy cloud. Early on, many texts fit, so each position drifts toward a blend of likely story words, mostly on its own. By the time the picture is clear, most positions have already settled. The model learned which words appear in stories but not which word goes next to which.

11

Prompt-conditioned continuation

inpainting the prompt

How

The 16 prompt positions are held at their exact embeddings during the whole ODE; only the other 48 positions move. The prompt comes out unchanged in 100% of samples.

Does the model use it?

Little. Only 46% of continuations re-use a name the prompt introduces ("a little bear named Benny"): AR-5.3M 78%, real 95%, random words 17%. Without any prompt (64 tokens from noise) the flow model still writes word salad (perplexity 51,985; AR-5.3M from scratch: 13.4).

Repository and final report

Phases 15–16

flow/ holds the code (dataset, embeddings, path, model, training, ODE sampler, generation, evaluation, diagnostics, comparison, benchmark, errors, plots); configs/ the settings and pre-registered hypotheses; results/ every metric, every generated continuation, the review files and the figures; INSTRUCTIONS.md all 16 phases with numbers. All training took about 2.5 CPU-hours; everything reproduces in about 3.5 hours from the commands in the README.

Lessons

  • A low loss is not good text. The flow loss fell for the whole run, the text did not improve. Always measure what you care about directly.
  • The hard part of continuous text generation is coordination, not rounding. Words are far apart and easy to round to; the model's points simply end up between words, chosen almost independently per position.
  • Masked diffusion has a built-in advantage: once it commits a token, later steps see a real word. The continuous flow only sees blurry blends until the end.
  • Surprises are results. Four of the ablation predictions were wrong, and the flow model is faster than expected. Writing predictions down first makes that visible.
  • What would plausibly help (not tested): self-conditioning, many more steps where tokens get decided, a learned lower-dimensional space with a decoder, much more compute, or discrete flow matching over token probabilities.
